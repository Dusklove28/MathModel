# 问题二阶段 1 验收与阶段 2 实验计划

## 范围与口径

本报告核对 `artifacts/problem2_stage1_baseline_full/` 的场景 B 基线。100 个输入图、固定 `data/config.txt`、官方 `code/multicore_cut_evaluate_problem_2.py` 和保存的候选方案构成数值证据。官方加速比以整图单核 `single` 方案为分母；其他单核切图候选仅作诊断，不替换题目规定的单核基准。

当前仓库的 Windows 工作区使用 CRLF，实验所在 Linux 环境使用 LF。对源码和配置的文本换行统一为 LF 后，`run_problem2_baseline.py`、`candidate_manager_problem2.py`、`solver_problem1.py`、`data/config.txt` 和全部八个官方评估器依赖文件的 SHA-256 均与 `run_identity.json` 一致。原始字节哈希跨环境不同只反映换行格式；跨环境缓存仍须按照运行器的原始哈希规则重新验证，不能直接复用旧缓存。

## 结论与保留事项

阶段 1 的数据覆盖、合法性、冻结探针、运行器基础测试和跨环境小规模复现均已通过，可以进入阶段 2 的**有限预算原型与配对实验**。原 `run_identity.json` 的 `git_head` 为空，且最后一次全量进度的 500 组均为 `resumed_valid_group`；这表示最后一次调用验证并复用了既有组，不代表一次新的完整冷启动测时。原始记录应保留，当前 Git 提交和 Windows 冒烟复现应作为补充溯源，不回填历史字段。完整冷启动墙钟时间仍须在新的空目录单独测量。

独立只读质检回执为 **PASS（阶段 1 技术继续判据）**：没有 P0/P1 问题；核查了全量统计、九组冻结探针、当前 Windows smoke、9 项测试，并抽检 `case_001/k2`、`case_050/k4`、`case_100/k5` 的组内追踪文件。它未逐文件重算全部 12,149 个 JSON 的哈希，也未重新执行全量官方评估。旧计划要求的“全量实验预算事先获准”无法由现存产物证明，属于独立的流程记录缺口；本报告不补造历史审批。

## 阶段 2 的执行顺序与预算

1. 固定原有五类非 `single` 切图，先只改变子图到核心的映射及合法核内顺序。保留相同 case、核数、切图和官方评估口径的原映射作为配对对照。每个局部候选先做 DAG、核内顺序与官方 plan 合法性校验，再以官方 Makespan 决定是否保留；估计模型只负责筛选。
2. 在 `case_001`、`case_050`、`case_100` 的 2/4/5 核上做最小纵向实验，先核对映射变更、继承关系、指标及可复现记录，再扩大搜索。不得从这三例直接调定面向 100 例的规则。
3. 后续配对试验建议按低加速、继承获益、长尾和原探针分层，先用 12 例：`001, 016, 024, 044, 047, 048, 050, 051, 058, 064, 067, 100`。若每例取 2–5 核、五类切图和每类一种新映射，则为 240 对、最多 480 次原映射与新映射官方评估。历史这 12 例相应原候选的冷缓存估计均值约 5.25 秒；按此粗估，480 次约 42 分钟单工作进程等效时间。新搜索和 Windows 环境耗时可能不同，须以最小实验重新校准；不假定多工作进程线性加速。
4. 记录全部尝试、合法性、官方 Makespan、新增搬运、Spill、跨核有效载荷、传输数、每核利用率、求解和评估耗时。配对比较至少报告逐例差值、均值、中位数、尾部与失败率。低核继承和核内排序另列消融，不与映射改进混称一种方法。

阶段 2 不直接进入 100 例全量实验。只有最小实验通过独立质检、配对结果显示方法有效且更新了时间预算，才扩大样本。
